■Q1. A〜Gの式や判定の誤り・注意点
【事実】
・A（ダウ理論）：左右 n 本の高値・安値（フラクタル構造）を用いる場合、スイングが確定するのは「頂点から n 本の足が経過した後」です。過去のチャートに当てはめる際、未来の n 本を参照して判定すると先読みバイアス（リペイント）が発生します。
・B（エリオット波動）：提示された3原則（2波が1波始点を割らない、3波が最短でない、4波が1波の価格帯に入らない）は標準的な定義と一致します。「第5波が第3波終点を超えない＝フェイラー（未達）」の扱いも整合しています。ただし、レバレッジ市場（FX）ではヒゲによる一時的な重複（4波が1波領域にわずかに侵入するケース）が頻発するため、終値ベースか高値・安値ベースかの定義が必要です。
・C（フィボナッチ）：戻し（0.236〜0.786）および延長（1.272〜2.618）の比率はすべて標準的な値です。
・D（重要計算）：
・ケリー基準の式 「W −（1−W）÷ R」（W:勝率、R:ペイオフレシオ＝平均利益÷平均損失）は数学的に正しい式です。ただし、取引ごとに利確・損切り幅が異なる戦略では、単純勝率・平均損益比によるケリー式は理論上の最適値と乖離します。
・ATRの計算において、真の値幅（True Range）は 「max（高値−安値, |高値−前日終値|, |安値−前日終値|）」 であり、その単純移動平均（SMA）または指数平滑移動平均（RMA/Wilder法）のいずれを使うかで値が変わります。MT5標準の iATR と合わせるならWilder法（平滑化）の採用が推奨されます。
・平均損益の t 区間について、FXの損益分布（特に両建て・ヘッジ解消を伴うもの）は正規分布から大きく外れ、強い歪度（スキュー）やファットテールを持ちます。サンプル数が少ない段階では t 区間の信頼性が低下します。
・G（k-means）：k-meansはユークリッド距離を用いるため、入力変数（保有秒数、pips、損益額など）のスケール（単位の桁数）が異なると、数値の大きい変数（保有秒数など）に分類が支配されます。計算前に標準化（Z-score）または正規化（Min-Max）が必須です。
【推測】
・Bのエリオット波動を単純な「交互の5スイング」に機械的に当てはめると、調整波（ABC波など）まで推進5波として誤判定する可能性が高いと考えられます。
【未確認】
・Artifact（v17）のコード内において、Aのスイング判定が「確定足（n 本遅れ）」で処理されているか、Gのk-meansの前に標準化処理が入っているかは実コード未確認です。

■Q2. F（判断アドバイス）で未達取引を「min（実損益, −コスト）」とすることの妥当性と代替案
【事実】
・min（実損益, −コスト） という式は、実損益がプラス（例：最大伸び x には届かなかったが、微益で逃げた取引）であっても強制的に「−コスト（マイナス）」に切り下げる処理です。
【推測】
・評価：保守的すぎます（特に小さな x と大きな x の比較を歪めます）。
・理由：目標利確幅 x を大きく設定するほど「未達」になる取引が増えます。未達になった微益撤退トレードをすべて「−コスト」に強制変換すると、大きな x の期待値が実態以上に急激に悪化するため、最適化アルゴリズムが「極端に小さな x（スキャルピング領域）」ばかりを最良と判定するバイアスがかかります。
・代替案（3段階の切り替え方式）：
（1）実績そのまま方式（推奨）：未達の取引は、決済ロジック（HedgeCutLoop）が実際に機能した結果であるため、切り下げずにそのまま「実損益（手数料・スワップ込み）」を使う。
（2）MFE/MAE比率による減衰方式：最大伸び（MFE）が x に届かなかった場合でも、実損益をそのまま使う案と、保守的評価（min（実損益, −コスト））の両方を画面に並記し、人間が幅を見て判断できるようにする。
【未確認】
・実際の HedgeCutLoop の決済において、利確未達時の微益撤退が全取引の何割を占めるかは実データ未確認です。

■Q3. Fの過剰最適化（カーブフィッティング）対策としての期間分割
【事実】
・同一データセット内で x を 0.5 pips 刻みで全探索して最大期待値を選ぶ手法は、サンプル数が少ない場合、偶発的なスパイク（たまたまそこまで伸びた数件の取引）に過剰適合します。
【推測】

■Q4. E（破産確率）における取引の独立性と「連敗の固まり」の反映
【事実】
・両建て戦略やヘッジループ戦略では、複数のポジションが同一の相場環境（急変動やレンジブレイク）で同時に処理されるため、損益結果に強い自己相関（クラスタリング）が生じます。単純な一様ランダム抽出（i.i.d.ブートストラップ）では、この連続性が破壊されます。
【推測】
・反映する必要があります。 独立とみなすと、相場急変時に発生する「同時・連続的なドローダウン」を過小評価し、破産確率が実態より甘く（低く）出ます。
・具体的な代替案（2つの実装案）：
（1）ブロック・ブートストラップ法（Block Bootstrap）：1取引ずつではなく、「連続する k 件の取引（例：k=5 または 10）」を1つのブロックとしてまとめ、ブロック単位でランダムに復元抽出する。
（2）決済タイムスタンプのグループ化：同じ分（または同じ時間）に同時決済された複数ポジション（両建ての同時解消など）の損益を合算して「1回のバスケット取引」とみなした上でブートストラップにかける。特に両建て戦略ではこの「バスケット化」が不可欠です。
【未確認】
・現在のCSV/スプレッドシート出力データに、同時決済を束ねるためのグループIDやミリ秒単位の決済時刻が含まれているかは未確認です。

■Q5. 実データで最初に確かめるべき項目と必要な取引数の目安
【事実】
・統計学における中心極限定理の一般的な目安として、母平均の推定には最低 N = 30 が下限とされますが、歪度の大きい分布（FXの損益など）ではより多くのサンプルが必要です。
・また、二項分布（勝率 p）の95%信頼区間（Wilson区間など）の誤差幅を ±10% 以内に収めるには、最悪ケース（p=0.5）で 「N ≈ 1.96² × 0.5 × 0.5 ÷ 0.10² ≈ 96」 件が必要です。
【推測】
・最初に確かめるべき項目：
（1）「口座の実残高の増減」と「記録された純損益（損益＋手数料＋スワップ）の合計」の完全一致（ロガーの欠損・重複・計算漏れの有無）。
（2）スプレッド拡大時のMFE（最大伸び）/ MAE（最大逆行）の異常値チェック（早朝ロールオーバー時の異常スプレッドでMAEが跳ね上がっていないか）。
・必要な取引数の目安（3段階）：
第1段階（ロガー動作・通信検証）：10〜20取引（または同時決済バスケット5〜10回分）。計算の正確性とWebRequestの疎通確認にはこれで十分です。
第2段階（基本統計量・期待値の初期評価）：100取引（根拠：勝率の95%信頼区間の誤差を約 ±10% 以内に抑えるための統計的目安）。
第3段階（Fの利確幅 x の最適化・Gのクラスタリング）：200〜300取引以上（根拠：前半・後半の期間分割検証を行うため、各期間に最低100取引ずつ確保する必要があるため）。

■2. 設計の確認（T019：Q6〜Q8）

■Q6. 両建て時の最大伸び（MFE）／最大逆行（MAE）の対応づけと注意点
【事実】
・MT5（MQL5）のヘッジング口座では、各ポジションに固有の POSITION_IDENTIFIER（またはポジションチケット）が付与され、エントリー（DEAL_ENTRY_IN）から決済（DEAL_ENTRY_OUT）まで同一のIDで追跡可能です。
・買い（POSITION_TYPE_BUY）は「建値（Open Price）＝Ask、現在値（決済評価）＝Bid」、売り（POSITION_TYPE_SELL）は「建値＝Bid、現在値（決済評価）＝Ask」で計算されます。
【推測】
・正しく対応づけるための注意点（3点）：
（1）追跡キーの厳格化：銘柄名（Symbol）だけでなく、必ず POSITION_IDENTIFIER をキーにした連想配列（または構造体配列）でMFE/MAEを管理する必要があります。
（2）Bid/Askの使い分け：ティックごとの更新時、買いポジションの伸び・逆行は現在の Bid と建値を比較し、売りポジションは現在の Ask と建値を比較する必要があります。ここを両方Bid（または仲値）で計算すると、スプレッド分の誤差が常時乗ります。
（3）部分決済（DEAL_ENTRY_INOUT や分割決済）とEA再起動への対策：VPSの再起動やMT5の再接続が起きた際、メモリ（RAM）上の変数だけでMFE/MAEを追跡していると、保有中ポジションの過去の最大伸び・逆行データが0にリセットされます。定期的（または変動更新時）にローカルファイルへ状態を退避（永続化）する仕組みがない場合、再起動をまたいだ取引のMFE/MAEは不正確になります。

■Q7. WebRequest の失敗・再送・重複対策で不足している点
【事実】
・MQL5の WebRequest 関数は同期通信であり、ネットワーク遅延やGoogle Apps Script（GAS）側のコールドスタート（初回起動遅延）によりタイムアウトやHTTPエラー（500系/429等）が発生することがあります。
・また、GASの doPost は処理完了後にリダイレクト（HTTP 302）を返す仕様があり、クライアント側がレスポンスを受け取る前にタイムアウトした場合でも、「GAS側ではスプレッドシートへの書き込みが成功している」というケース（結果不明状態）が起こり得ます。
【推測】
・再送（リトライ）を行うと、上記のタイムアウト時に「同じ決済データが2回スプレッドシートに書き込まれる（重複）」が確実に発生します。
・追加すべき対策（3点）：
（1）冪等性（べきとうせい）の担保（GAS側の重複排除）：送信データに一意のキーとして deal_ticket（約定チケット番号）を含め、GAS側でスプレッドシートに書き込む前に「すでに同じ deal_ticket が存在すれば追記せず成功レスポンスだけ返す（スキップする）」処理を入れる。これが最も確実な重複防止策です。
（2）未送信キューのローカルファイル退避（永続化）：送信待ちキューをメモリ上だけに置くと、WebRequest失敗中にMT5が再起動した際にログが永久に失われます。決済発生時はまずローカルの未送信ファイル（CSVまたはバイナリ）に即座に書き出し、送信成功が確認できたものから削除（または送信済みフラグを付与）する2段階設計が安全です。
（3）リトライ上限とバックオフ：2秒ごとに毎回失敗し続けると無限ループになるため、リトライ回数上限（または失敗時は次回送信まで10秒空ける等の待機処理）を設ける必要があります。
【未確認】
・現在の FXTradeLogger.mqh および受け手側のGASスクリプトに、deal_ticket による重複チェックが入っているかは未確認です。

■Q8. 送信処理がEAの売買判断（HedgeCutLoop）を遅らせる恐れ
【事実】
・MQL5において、1つのEA内の OnTick、OnTimer、OnTradeTransaction は単一スレッド（シングルスレッド）のイベントキューで順番に処理されます。別スレッドで並列実行されるわけではありません。
・したがって、OnTimer の中で WebRequest を実行している間、その通信が完了（またはタイムアウト）するまで、後から到着した OnTick や OnTradeTransaction の処理は完全にブロック（待機）されます。
・GASへの WebRequest は通常でも 0.5秒〜2秒程度、GASがスリープ状態からの起動になると 3秒〜5秒以上かかることがあります。また、1回の OnTimer で「最大5件」を1件ずつ5回 WebRequest すると、最悪の場合 5秒〜15秒近くEAのメインロジック（ヘッジや損切り判定）がフリーズします。
【推測】
・売買判断を遅らせる恐れが極めて高いです（今回の設計の中で最大のリスク要因です）。
・相場急変時に複数ポジションが一斉決済された直後、OnTimer が発火してGASへの送信に数秒間ブロックされると、次のヘッジエントリーや緊急決済のタイミングを逃す危険があります。
・具体的な代替案（3つの対策）：
（1）バッチ送信化（1回のWebRequestにまとめる）：最大5件を送る際、5回 WebRequest を呼ぶのではなく、5件分のJSON配列を1つのペイロードにまとめて1回の WebRequest で送信する。
（2）タイムアウトの短縮：WebRequest の timeout 引数を短め（例：1000〜2000ミリ秒）に設定し、長時間のフリーズを防ぐ。
（3）【最推奨】送信用EA（サブEA）の分離：MQL5は「1つのチャート（1つのEA）につき1スレッド」で動きます。したがって、HedgeCutLoop 本体では WebRequest を一切行わず、超高速なローカルファイル（FILE_COMMON）への書き出しだけを行います。そして、別のチャートに「ログ送信専用の軽量EA」を貼り付け、その別EAの OnTimer からファイルを読み取って WebRequest でGASへ送るように分離すれば、HedgeCutLoop の売買判断およびMFE/MAE追跡は 0.001秒も遅延しなくなります。
