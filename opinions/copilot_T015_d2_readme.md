# T015-(d-2) README・memory.jsonの重複・相違点（案）

この文書は照合結果の案であり、README.md と memory.json は変更していない。ここでは既存記述の確認と、解釈・未確認事項を分ける。

## 事実（記載内容の照合）

- **T003の目的は重複している。** README.md のT003節は担当別の更新範囲、タイムスタンプ、更新時の必須項目を説明している（README.md 81–144行）。memory.json の `共有データ.タスク` にあるT003も、担当別の書き込みルールと「最終更新」「最終実行」の更新を扱う。
- **T003の状態・完了条件には相違がある。** README.md はT003を「完了」と記載し（81–89行）、ルールが memory.json と README.md に記載されることを完了条件としている（88行）。一方、memory.json のT003は「未着手」で、完了条件は memory.json の備考またはREADME.mdへの記載となっている。
- **備考の必須性はREADME.md内で一致していない。** T003の更新例では備考記録は「オプション」（137行）だが、記載場所の説明ではmemory.jsonの備考セクションが「必須」（244行）とされている。
- **T006の検証条件はmemory.jsonにあるが、README.mdにT006の記載は見当たらない。** memory.json のT006は、AIの「完了・構築済み」報告をGitHubの実ファイルで確認してから記録するルールを扱い、状態は「進行中」、完了条件はREADME.mdへの追記としている。README.mdの統一報告ルール（201–239、356–370行）は根拠・検証内容や報告の流れに触れるが、T006の「GitHubの実ファイルで確認」という条件を明記していない。
- **RULE-01とRULE-04は協議を経た結論の扱いを重ねている。** RULE-01は他agentの意見収集・精査を結論報告の条件とし、RULE-04は協議結果がそろうまで決定・推奨・採用案・改善率を記録しないとしている。
- **RULE-02とRULE-04は更新時の保全手順を重ねている。** RULE-02は直前SHAを土台にし他項目を変更しないこと、ユーザー承認前に「決定」と記載しないことを定める。RULE-04も更新前SHA、差分、JSON検証、復元可能な履歴とユーザー承認を含む更新順を記す。
- **緊急時の記載は異なる範囲を扱う。** RULE-03は緊急事項の即時報告と、ユーザーが明示した場合の協議なしの即時実行を記す。RULE-04は協議結果がそろうまでの決定等の記録制限を定める。
- **統一報告節は継続実行・更新を促す。** README.md 356–370行は、指示がなくてもタスク実行・報告・更新を継続すると記載する。また、201–222行は次のステップや「最終判定」を報告形式に含める。RULE-04はユーザー承認を含むGitHub更新手順と、協議前の推奨等の記録制限を定める。

## 推測（運用上の影響）

- T003の状態と完了条件、備考の必須性の相違は、更新担当や完了判定を読むagentに異なる解釈を生じさせる可能性がある。
- 統一報告節の継続更新や「最終判定」は、RULE-04の承認・協議条件と合わせて読む必要がある。これらがどの場合に優先されるかは、上記記載だけでは一意に決められない。
- RULE-03の緊急時の例外がRULE-04の記録制限にどこまで適用されるかは、追記または確認が必要になる可能性がある。
