### 推す案（暫定・意見）
【推測】デモ口座の段階では、「R4（MQL5 VPS）で EA を常時稼働」と「R1 または R2 で iPhone からの指示・監視」を分けて考える案を推します。常時稼働とAI操作を別の役割に分けると、Windows 365 の休止に左右されにくくなるためです。
理由は下のQ1〜Q4に記します。

### Q1 最も手作業が少なく確実なのはどれか
- 【事実】memory.json の D004 に、R1〜R4 の記載（R1: Claude Code＋Remote Control、R2: ChatGPT/Codex＋Remote、R3: MT5内蔵AIのみ、R4: MQL5 VPS）があります。
- 【推測】手作業の少なさは、「iPhoneだけで指示できるか」と「Windows 365 を起こす操作が要るか」で変わります。R3 は毎回 Windows App 接続が必要と D004 に書かれており、iPhone中心には向きません。R4 は EA の常時稼働のみで、AI操作はできないと記載されています。
- 【推測】R1 と R2 は iPhone からの指示という点で条件に合いますが、いずれも Windows 365 が起動していることが前提のはずです。これは D004 の共通の制約からの推論です。
- 【未確認】R1・R2 の Remote 機能の実際の動作、MT5 MCP の対応状況、各プランの利用条件は、公式ページを開けていないため確認できていません。「確実」と言える比較は現時点でできません。

### Q2 R1〜R4以外の方法
- 【推測】通常の Windows VPS 上で MT5 を動かす案。常時稼働でき、Windows 365 の休止の影響を受けません。保守（OS更新、アクセス制御、バックアップ）の負担と費用が増えます。
- 【推測】iPhone からの指示を、停止・再開・状態照会など限定された操作に絞る案。自由文の指示を直接注文に変換することは、初期段階では避けたほうがよいと考えます。
- 【未確認】上の案が MT5 と EA の実装で動くか、必要な権限があるかは確認していません。

### Q3 Windows 365 の休止（切断1時間後）を避ける方法

## 3. D005（窓口を1つにする方法）

### 窓口方式の比較
【事実】memory.json の D005 には、(a) API直接、(b) Zapier経由、(c) 各AIがGitHubにCommit、(d) 窓口1つ＋必要時Gemini の比較が既にあります。D005 の「Claude内部協議」は、他agentの意見がないため撤回と記載されています。
【推測】その上で、GitHub を共有台帳にする場合の各方式の比較は次のとおりです。

| 方式 | 強み | 制約・懸念 |
|---|---|---|
| Issue | 依頼ごとにスレッドで残る。iPhone の GitHub アプリで読み書きしやすい | 構造化データには向かない。memory.json との整合は別途必要 |
| Discussion | 議論向き。回答の収集に向く | リポジトリで有効化されているかは未確認 |
| Pull Request | 差分・レビュー・承認が残る。承認後にだけマージできる | 競合解消は iPhone のみだと操作負荷が高い |
| 担当別更新（memory.json の分割等） | 同時更新の衝突を減らせる | ファイル構成の変更が必要。ユーザー承認が必要 |

【推測】memory.json のような単一ファイルを複数agentが更新すると衝突しやすいため、更新はPR経由にし、各agentの意見は別ファイル（例：opinions/）で集める形が、現状の制約に合うと考えます。この PR の `opinions/` はその一例です。

### 実現条件・制約・必要な権限
- 【事実】GitHub Actions のワークフローは、workflow_dispatch を設定すれば、Actions タブ、GitHub CLI、REST API から手動で起動できます。起動にはリポジトリへの書き込み権限が必要で、ワークフローファイルはデフォルトブランチにある必要があります（上記の開けたURL）。
- 【推測】各agentが記録を書くには、そのagentが書き込み権限を持つ必要があります。D005 には ChatGPT・Gemini の GitHub アプリは書き込み不可との記載があります（出典は未確認）。
- 【推測】他社のAIを自動で相互に呼び出すには、API、認証、料金、秘密情報の管理が必要です。GitHub Actions だけでは実現しません。
- 【未確認】各AIのAPI契約状況、Zapier の接続状況、Discussion の有効化、GitHub のブランチ保護設定。

### ログと承認方法
- 【推測】依頼・回答・変更案を Issue か PR に残し、変更は PR の差分でユーザーが承認してからマージする。承認前にmainへ書かない。
- 【推測】memory.json の更新前に、更新前のSHAと最終更新の値を照合し、JSON構文を確認する。
- 【事実】既存ルールに「GitHubへの更新はユーザー承認後」とあります（T012・T013）。

- 【未確認】Claude・Gemini・ChatGPT のチャットへ直接メッセージを送ること、他社AIを自律的に操作すること。私にはできないと認識していますが、各サービスの仕様は確認していません。
