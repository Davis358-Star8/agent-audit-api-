# Copilot の意見（両建て損益計算機 v3）

本書は、main の `consultations/calculator_v3.md` に記載された式の精査です。計算機の実装そのものは提供されていないため、式と提示された検算例を対象にしています。memory.json と main は変更していません。

## 根拠と確認範囲

- 【事実】main の協議文を読みました（取得したファイル SHA: `3ba518b0e7ea5b25eba2293f6a6671ec51e0c049`）。
- 【事実】この環境から XM / XMTrading の公式ページを開けませんでした。実際に開けた XM の根拠 URL はありません。
- 【未確認】XM の口座法人、口座通貨、商品ごとの契約仕様、証拠金ルール、スワップ、手数料および強制決済条件。以下では依頼文に記載されたXM仕様を、独立に確認済みの事実として扱いません。

## 1. 計算式の精査

| 対象 | 判定・理由 | 修正または適用条件 |
|---|---|---|
| `d=(bid+sp1/2)-(c.b0+sp0/2)`、`half=(sp0+sp1)/2`、`p:dir*d*k`、`s:-half*k` | 【事実・数式】開始時と現在のスプレッドを同じ価格単位に直し、`bid` が現在Bid、`b0` が開始時Bidなら、線形契約の買いは `(bid - (b0 + sp0))*k`、売りは `(b0 - (bid + sp1))*k` と一致します。この形でのスプレッド二重計上という指摘は当たりません。 | 【推測】実際の約定価格を使う場合は、買いの開始Ask・売りの開始Bidと、決済時の実際のBid/Askを直接使う方法が明瞭です。推定スプレッドを使う場合は約定価格に同じスプレッドを重ねて差し引かないようにします。 |
| `l:-slip*k` | 【未確認】`slip` が「各ポジションの決済1回あたりの不利な滑り」を意味する場合は、両方に負のコストを置く考え方は整合します。1回分の滑りか往復合計か、また新規時の滑りを含むかは入力定義から分かりません。 | `slip` の単位と対象約定（新規・決済、片道・往復）を固定します。実約定価格を入力する場合、既に価格に含まれた滑りを再度差し引かないようにします。 |
| `-c.comm*lot*c.commConv` | 【未確認】`comm` が片道か往復か、すでに口座履歴の残高に計上された費用かが未定義です。往復手数料/lotを使って一連の取引コストを見積もるなら、各ポジションに1回ずつ適用する形は整合します。 | 取引全体の予測値なら、手数料率の単位と新規・決済の課金を明示します。実績の口座残高を起点にする場合、既に残高へ反映された手数料を再度加算しません。換算通貨・換算時点も入力対象にします。 |
| `sw*lot*c.days` | 【事実・数式】日数に同一レートを掛ける式は、レートが毎日一定で、課金日数と保有日数が等しい場合に限った近似です。 | 【推測】実績または予定のロールオーバーごとのレートを合計する形が適切です：`swapNet = lot * Σ(swapRate(direction, symbol, rollover))`。レートがポイント建てなら各ロールオーバー時のポイント価値と口座通貨換算を別途適用します。 |
| `mB=lotB*cs*price円/lev`、`mS=...` | 【未確認】この形は、`price円` が契約数量あたりの価格を口座通貨へ換算した値であり、適用レバレッジが一定、対象商品が線形である場合の概算です。`price円` の定義、商品別証拠金率、レバレッジ段階の扱いは記載されていません。 | 商品仕様に応じて必要証拠金を口座通貨で算出します。価格・換算レート・レバレッジまたは証拠金率を再評価できるようにします。 |
| `両建て中=|mB−mS|` | 【未確認】「同量は証拠金ゼロ、差分だけ必要」というXMの適用条件をこの環境では確認できていません。式は、同一商品のヘッジ部分に証拠金がかからず、差分部分に通常の証拠金がかかる場合だけ成立します。 | 同一商品でヘッジ部分・非ヘッジ部分の単位証拠金が定義できる場合の一般形は `M = mH*min(lotB,lotS) + mU*abs(lotB-lotS)` です。`mH=0` と置くのは口座・商品別仕様で確認できた場合だけにします。 |
| `フルロット=残高*lev/(cs*price円)` | 【事実・数式】これは単純化した必要証拠金が残高と等しくなる境界で、実際に使える最大ロットとは言えません。 | 利用可能証拠金、既存ポジション、必要な余裕、スプレッド等による評価損、手数料、レバレッジ段階を含め、商品別の必要証拠金を解いてください。とくに両建て解除後の片側必要証拠金も検査対象です。 |
| `目標までの値動き=(目標−Lnet−Wnet)/per` | 【事実・数式】目標が「決済済み側と残存側を合算した損益」で、`Lnet` と `Wnet` が同じ時点・同じ費用範囲のネット損益なら、価格変化の**大きさ**を求める式として使えます。 | 価格の符号も返す式は `ΔP=(目標−Lnet−Wnet)/(dir*lot*cs*conv)` です。`per` は正の大きさなので、現行式だけでは有利方向/不利方向を表しません。目標が残存側単体の利益を指すなら、`Lnet` は目標から除外します。目標到達までの保有時間を見込む場合、残存側に今後発生するスワップ等も損益へ反映します。 |
| `eq=残高+Lnet+Wnet` | 【未確認】`残高` が取引前残高なら、決済損益と残存建玉の評価損益を加える考え方です。片側決済後の現在残高を使うなら、`Lnet` が既に残高へ反映されて二重計上になる可能性があります。 | 起点を明示します。取引前残高なら `eq = balanceBefore + realizedNet + remainingFloatingNet`。決済後の現在残高なら `eq = currentBalance + remainingFloatingNet`（いずれも他の残高要素・建玉がない場合）。 |
| `維持率=eq/証拠金` | 【事実・数式】比率としてはこの式です。百分率の「維持率」を表示するなら100倍が必要です。 | 比率で表示するなら「維持率比」と明記し、百分率なら `marginLevelPct=100*equity/usedMargin` とします。証拠金が0の場合も除算を避けます。 |
| `ロスカットまでの逆行=(eq−0.2×証拠金)/per` | 【事実・数式】`per` が正の値なので、この式だけでは逆行方向の符号を表せません。証拠金一定・他の建玉なし・損益線形という仮定下での符号付き価格変化は `ΔP=(0.2*M−eq)/(dir*lot*cs*conv)` です。 | 【未確認】強制決済の実際の閾値と証拠金再計算は口座・商品別ルールを確認できていません。この式は閾値到達の概算に限定し、価格変化に伴う必要証拠金・換算レート・他建玉を再計算しない限り「ロスカットまでの距離」と断定しないでください。 |
| 比率 `|小さい側|÷伸びている側` | 【事実・数式】分母が正の場合に限って定義できます。 | 分母が0以下、損益が同額、損益の符号が変わる場合は「算出不可」等を返し、無限大・NaNを画面に出さないようにします。 |

### 検算例

- 【事実・数式】提示されたUSDJPY例は、各0.05 lot、契約サイズ100,000、換算1、スプレッドが開始・現在とも0.7 pip、滑り・手数料・スワップなしという入力条件では、1 pipあたり50円/ポジションとなり、10 pip上昇時の買い +465円、売り −535円、合計 −70円と一致します。
- 【事実・数式】同じ単純化条件で、買い損益と売り損益の比率が1:3になる上昇幅は1.4 pipです。売り決済後の取引合算損益を300円にするには、そこからさらに7.4 pipの上昇が必要という提示値も、価格感応度50円/pipで整合します。
- 【未確認】この算術確認は入力された仕様を使った検算であり、XMでの実際のスプレッド、手数料、証拠金、約定を確認したものではありません。

## 2. 抜けているコスト・リスク

- 【推測】スプレッド拡大、価格ギャップ、急変時の実約定差、部分約定、注文拒否・決済遅延。滑りを固定値にしても実際の損失上限を保証しません。
- 【未確認】商品・口座別のロールオーバー日時、買い/売りスワップ、休日調整、複数日分のスワップ課金、適用通貨と換算方法。
- 【推測】片側決済後に目標到達まで保有する期間の追加スワップ。現時点までの費用だけを使うと、その先のネット損益を過大に見積もる場合があります。
- 【未確認】口座通貨がJPY以外の場合の損益・手数料・スワップの換算方法と換算時点。EURUSD・GOLDの `conv=USDJPYレート` は、JPY口座でUSD建て損益を換算する想定に限られます。
- 【推測】同量両建てを解除した瞬間に増える必要証拠金、スプレッドや評価損で下がる有効証拠金、他の建玉・クレジット等を含めた口座全体の証拠金維持率。
- 【未確認】GOLDを含む各シンボルの契約サイズ、tick size/value、損益計算方式、最小数量・数量刻み、価格桁数。`pip` と `cs` の固定値だけでは商品仕様の変更やシンボル差を検出できません。
- 【推測】両方の建玉を順番に閉じる際の価格変動・執行順序。2件を同時の同一価格で閉じられるという前提は置けません。

## 3. XM仕様との相違・確認状況

- 【事実】この環境ではXM公式資料を開けておらず、根拠URLとして提示できるページはありません。
- 【未確認】協議文の「ヘッジ中の証拠金ゼロ」「片側決済後は通常証拠金」「レバレッジ上限・段階」「マージンコール/ストップアウト水準」「口座別平均スプレッド」「Zero口座の手数料」「両側のスワップ課金」は、いずれもXMの対象法人・口座・銘柄・時点に適用されるかを独立確認できていません。
- 【推測】MT5の対象口座で各シンボルの仕様を確認し、XMの同じ法人・口座区分の公式資料および口座画面と突き合わせる必要があります。平均スプレッドは固定スプレッドとして将来の実コストを保証する値にはなりません。
- 【未確認】GOLDの `1 lot=100オンス`、`1 pip=0.1ドル`、および同量でない両建てが差分のみの証拠金になるという前提。依頼文自身が未確認としているため、既定値に固定しないでください。

## 4. 改善案

### 優先度：高

1. 【推測】Bid/Ask、約定価格、スプレッド、pip/tick、契約サイズ、損益通貨、口座通貨換算をシンボル仕様に基づいて扱い、単位を画面にも表示する。
2. 【推測】損益目標とストップアウトの計算で方向（買い/売り）を保持する。維持率は比率か百分率かを明確にし、ゼロ証拠金・不足データ・目標到達済みを安全に処理する。
3. 【推測】スワップは保有日数の単純乗算ではなくロールオーバー単位で計算し、手数料の片道/往復と、既に残高へ反映された費用を区別する。
4. 【未確認】XMの対象口座・商品でヘッジ証拠金、レバレッジ段階、強制決済条件を確認するまで、それらの表示を「概算/要確認」とし、最大ロットやロスカット価格を確定値として示さない。

### 優先度：中

1. 【推測】スプレッド変動、滑り、為替換算変動、スワップ課金日、片側決済後の証拠金を変えたケースで、計算結果と単位をテストする。
2. 【推測】実口座の注文に接続する前に、MT5の対象シンボル仕様とデモ口座の約定・口座履歴を照合し、予測と実績の差を表示する。

### 優先度：低

1. 【推測】「取引全体のネット損益」「残存側単体の損益」「口座の有効証拠金」を別々に表示し、目標値がどの値に対するものか分かるようにする。
2. 【推測】入力値と最終更新時刻を結果に添え、固定・推定・実績の各コストが判別できるようにする。
